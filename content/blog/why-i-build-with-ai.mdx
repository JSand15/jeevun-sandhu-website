A question I get a lot: _if you're not writing the code yourself, are you really building it?_

I think that question assumes there's one legitimate way to build software, and I don't think that's true anymore.

## What I actually do

I scope the product, make the design and architecture decisions, and direct an AI engineering tool — Claude Code — to implement it. I review the output, push back when it's wrong, and iterate until it's right. That's a real skill. It's just a different one than typing every line by hand.

Here's roughly what that loop looks like for a new feature:

```txt
1. Define the problem and the smallest version that solves it
2. Direct the implementation
3. Use the product myself, break it on purpose
4. Fix what's broken, cut what's not needed
5. Ship
```

## Why this matters more than it used to

A few years ago, this wouldn't have worked. Directing an AI to build production software required either the AI to be much better than it was, or the human directing it to already know how to code well enough to catch every mistake. Neither was reliably true.

That's changed. Not because building got easier — it didn't — but because the bottleneck moved. The bottleneck now is judgment: knowing what's worth building, being able to evaluate whether an implementation is actually good, and being stubborn enough to keep iterating instead of accepting the first working version.

> The parts of building that used to require years of engineering experience are now more accessible. The parts that require taste, judgment, and persistence are not — and never will be.

## What I'm not claiming

I'm not claiming to be a senior engineer. I'm not claiming this approach is better than traditional engineering for every team or every problem. I'm claiming that for a 15-year-old with no funding and no team, this is the difference between having an idea and having a product two people actually use.

That's enough for me to keep doing it.
